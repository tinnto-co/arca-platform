- copilot-control.ts is a module-level bridge between AgentInput (outside CopilotKit subtree) and CopilotBottomPanel (inside)
- Actions that take a clientId should ALSO accept clientName as fallback — Gemini sometimes regenerates UUIDs incorrectly
- **CopilotKit per-screen hooks pattern**: dedicated client-only "registrar" components (return null) that mount inside `<CopilotKit>` provider. Use `useRouterState({ select: (s) => s.location.pathname })` to detect the active route and switch instructions reactively. See CopilotSuggestions.tsx — pattern reusable for AdditionalInstructions/FrontendTools too.
- **`useCopilotChatSuggestions` available values**: `'enabled' | 'disabled' | 'always' | 'before-first-message' | 'after-first-message'`. With `'enabled'` the hook internally maps it to `'always'`. Pass `'disabled'` to skip registration entirely on routes where you don't want suggestions.
- **Custom-event bridge for CopilotKit frontend tools → page state**: when a frontend tool needs to mutate component-level state in a different subtree (e.g. tab state in `client-detail-page.tsx` or `/sueldos`), dispatch a `CustomEvent` on `window` from the tool handler and add a `useEffect` listener on the page that calls `setActiveTab(e.detail.tab)`. Define the event name as a `const` and augment `WindowEventMap` so TS infers `e.detail` correctly. See `src/components/copilot/FrontendTools.tsx` (`ARCA_EVENT_SET_CLIENT_TAB`, `ARCA_EVENT_SET_SUELDOS_TAB`).
- **`useFrontendTool` enum params auto-narrow**: when you pass `enum: [...TUPLE]` in `parameters`, the handler receives `tab` typed as the union — TypeScript narrows to `never` in the false branch of a runtime guard. Coerce via `String(tab)` and validate with a separate type-guard helper that takes `string`, otherwise prettier/typescript-eslint complains about template literals on `never`.
- **Always `void navigate(...)` inside `useFrontendTool` handlers**: TanStack Router's `navigate()` returns a Promise; a non-async handler that drops it triggers `@typescript-eslint/no-floating-promises`. Same applies anywhere a non-async function calls navigate.

- **Learnings for future iterations:**
  - `useCopilotAdditionalInstructions` ya tiene cleanup automático: cuando el componente desmonta, o cuando `available` flipea a 'disabled', la línea de instructions se quita del system prompt. Por eso usar `available: instructions ? 'enabled' : 'disabled'` en lugar de un `if (!instructions) return null` mantiene la regla de hooks de React intacta y deja al hook hacer su propio toggle.
  - El array de dependencias del hook (`[instructions]`) es lo que dispara la re-registración cuando cambia la ruta. Sin ese array, la línea inicial se queda pegada al system prompt aunque cambies de pantalla — mismo gotcha que documentamos en US-001 para `useCopilotChatSuggestions`.
  - Tab-level instructions sin URL search params: el `<AdditionalInstructions />` corre arriba de los page components y no tiene acceso al `activeTab` que viven en estado local. Para soportarlo sin reestructurar, habría que: (a) llevar el tab a `useSearch()`, o (b) montar un segundo registrar adentro de cada page que lea su estado local. Para esta sprint se eligió (a)/(b)? — ninguno: collapse a un solo instruction por path. Documented the limitation en el JSDoc del componente.
  - Hard-limit 6 instructions: registramos 4 (clients/$id, clients, sueldos, notifications). Cada vez que se agregue una nueva, revisar si conviene fusionarla a alguna existente para evitar que el system prompt se infle y el modelo se confunda con reglas que no aplican a la pantalla actual.
  - Las 3 rutas Copilot registrars (`CopilotSuggestions`, `FrontendTools`, `AdditionalInstructions`) comparten exactamente el mismo patrón: client-only, return null, mounted dentro de `<CopilotKit>`, dispatchean según `useRouterState`. Si nace una 4ta o 5ta, vale extraer un `useRoutePathname()` helper, pero por ahora 3 instancias inline es ok (regla de tres).

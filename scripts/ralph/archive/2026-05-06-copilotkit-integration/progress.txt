- Reusing dashboard KPI components in inline AI render: prefer extending the existing component with an optional pre-fetched data prop (like US-005's `items` and US-006's `stats`) over creating a new wrapper. When the prop is provided, gate the matching `useQuery` with `enabled: !skipQuery`. Other independent queries the component runs (e.g., `getOverdueDebts`, `getPendingNotificationsCount`) keep running and benefit from React Query cache reuse if the dashboard is already cached.
- The existing AI agent at src/routes/api/agent.ts uses Vercel AI SDK v6 (`ToolLoopAgent`, `gemini-2.5-flash`) and is read-only (SQL SELECT only). It MUST NOT be modified.
- The /chat page at src/routes/_authed/chat/{$id,index}.tsx uses @ai-sdk/react useChat with /api/agent endpoint. It MUST keep working unchanged.
- CopilotKit runs in PARALLEL to the existing agent — separate runtime endpoint at /api/copilotkit, separate floating UI (CopilotPopup), shared Gemini API key.
- Module gating: every feature in this PRD must respect the `ai_agent` module flag (listOrgModules from src/actions/admin.tsx, useQuery key ['orgModules']).
- Multi-tenancy: every server function calls getSessionWithOrg() first, scopes by orgId.
- Never expose client.password (AFIP credential) in any context (readable, action result, log).
- TanStack Start route handler signature: `{ server: { handlers: { POST: async ({ request }) => Response } } }` — see src/routes/api/agent.ts for the canonical pattern.
- Module gate pattern (from US-055 of the previous Ralph run): `beforeLoad` with `throw redirect({ to: '/' })` requires `// eslint-disable-next-line @typescript-eslint/only-throw-error` before each throw.
- CopilotKit runtime endpoint (US-001): use `copilotRuntimeNextJSAppRouterEndpoint` from `@copilotkit/runtime` — its `handleRequest(req: Request)` works with TanStack Start's Web Request/Response model. No Node adapter needed. Pair with `GoogleGenerativeAIAdapter` and `process.env.GEMINI_API_KEY`.
- New routes under `src/routes/` only get into `src/routeTree.gen.ts` after the dev server (vite + tanstackStart plugin) runs once; until then `tsc` will complain. Run `bun run dev` briefly to regenerate.
- TS auth session shape: cast `(session.session as { activeOrganizationId?: string | null }).activeOrganizationId` — Better Auth doesn't type the org plugin field on the base type.
- Module gating (US-002): `listOrgModules` server fn in `src/actions/admin.tsx` reads `organization.metadata` (JSON string) → `{ ai_agent: boolean }`. Defaults to `{ ai_agent: true }` when metadata is null/invalid. Consume via `useQuery({ queryKey: ['orgModules'], queryFn: () => listOrgModules() })`. The hook returns `undefined` while loading — treat that as "disabled" and upgrade once data resolves so the provider is never blocking.
- `getSessionWithOrg()` returns `orgId` typed as `any` (helpers.ts uses `as any`). When passing to drizzle `eq()` in a NEW server function, cast at the call site: `const { orgId } = (await getSessionWithOrg()) as { orgId: string }` to avoid a fresh `no-unsafe-argument` lint error. Existing actions tolerate the error; new code shouldn't add to the count.
- CopilotKit provider must be conditional but NEVER block render of the shell. Render the shell first, wrap in `<CopilotKit runtimeUrl="/api/copilotkit" agent="default">` only when `aiAgentEnabled` is true. Import `@copilotkit/react-ui/styles.css` once at the top of the route file — CSS class names are scoped enough that they don't visually leak when no CopilotKit DOM is present.
- CopilotPopup (US-003): import `{ CopilotPopup }` from `@copilotkit/react-ui` and place it as a sibling of the shell *inside* the `<CopilotKit>` provider. It is a fixed-position floating button (bottom-right) so it does not shift layout. Hide it on `/chat` and `/chat/$id` to avoid double UI alongside the existing dedicated chat. Use `useRouterState({ select: (s) => s.location.pathname })` (already in scope) — `useLocation()` would also work but the existing route file uses `useRouterState`. Provide labels via `labels={{ title, initial, placeholder }}` — the `CopilotChatLabels` interface lives at node_modules/@copilotkit/react-ui/src/components/chat/ChatContext.tsx if you need to extend later.
- CopilotActions hook component (US-004+): client-only component that calls `useCopilotAction(...)` for each action and returns `null`. Mount it INSIDE `<CopilotKit>` provider but OUTSIDE the shell so the registrations live for the lifetime of the provider. New actions go in `src/components/copilot/CopilotActions.tsx`. Server fns that back actions live in `src/actions/copilot.tsx`.
- Generative UI render (US-004): `useCopilotAction` `render` prop receives `{ status, args, result }`. `status` is `'inProgress' | 'executing' | 'complete'`. Show a spinner while non-complete (Gemini may render the tool call before the handler returns). When `result` is undefined return a fallback. Cast `result` to your typed result via `result as MyResultType` since CopilotKit types it as `any`.
- Action `parameters` array uses `{ name, type: 'string' | 'number' | 'boolean', description, required }`. Optional params still arrive in handler args but may be `undefined` — coerce with `?? undefined` before passing to a Zod-validated server fn that uses `.optional()`.
- Reusing big stateful components in inline AI render (US-004): `RenderIvaResume` is heavy (own queries, editable rows, Excel export). Wrapping it works because it accepts `clientId`, `selectedProfileId`, `dateRange`, and a `clientIva` blob — all of which can be derived from the action's resolved client+profile+period. The wrapper (`CopilotIvaResume`) builds `clientIva` from the action result's `ivaScrape` row and lets RenderIvaResume re-query invoices itself. Don't try to feed pre-computed totals into RenderIvaResume — it computes from invoices via React Query. The action's role is *resolution* (name → uuid) and providing the AFIP scrape data, not pre-computation for display.
- React Hooks rules in conditional render: when a component branches on `'error' in result`, ALL hooks (`useState`, `useEffect`, etc.) MUST be called before the conditional return. Use `const isError = 'error' in result;` to extract the discriminator, then call hooks based on safe values (e.g. `const perfiles = isError ? [] : result.perfiles`), THEN do `if (isError) return <ErrorView />`.
- `dbReadonly.execute(sql.raw(...))` returns an iterable whose item type isn't `Record<string, unknown>` — drizzle types it loosely. ESLint flags `as Record<string, unknown>[]` as "unnecessary assertion". Workaround: type via `Iterable<{ field: type }>` cast on the source, then `Array.from(rows as Iterable<...>)` returns the right type without a no-unnecessary-type-assertion warning.
- useCopilotReadable safety (US-007): the hook calls `useCopilotKit()` internally, which subscribes to the runtime via `useEffect`. When the CopilotKit provider is NOT mounted, the default context value has `copilotkit: null`, so the subscribe call inside `useCopilotKit`'s effect would crash. Workaround: never call `useCopilotReadable` directly in pages that render outside the provider. Instead, gate via `useQuery({ queryKey: ['orgModules'] })` and only render a tiny `<CopilotReadableEntity description value />` wrapper component when `aiAgentEnabled` is true. The wrapper is at `src/components/copilot/CopilotReadableEntity.tsx` and is reusable for any "expose entity context to Copilot" need.
- HITL with `renderAndWaitForResponse` (US-008): the FrontendAction type is a discriminated union — when you set `renderAndWaitForResponse`, you CANNOT set `handler` (TS will reject the literal even though the PRD draft suggested both). The mutation that needs confirmation must be invoked from inside the rendered component itself. Pattern: render a stateful component (e.g. `<ScrapeConfirmation respond={respond} ... />`) that holds local phase state (`pending` → `submitting` → `done`/`failed`/`cancelled`), calls the server fn directly on confirm, then calls `respond({success, ...})` with the outcome so CopilotKit completes the action and the model gets a structured result. During `status === 'inProgress'` `respond` is `undefined` — show a placeholder; only render the confirmation UI when `status === 'executing' && respond` is defined.
- Generic HITL card (US-009): `src/components/copilot/ConfirmationCard.tsx` is a reusable confirmation card for any HITL flow. Props: `{ title?, description, confirmLabel?, cancelLabel?, submittingLabel?, successText?, respond, onConfirm }`. `onConfirm` is an async fn that runs the actual mutation and may throw — the card handles phases, success state, error display, and `respond(...)` plumbing. Only build a bespoke `<XxxConfirmation>` if you need extra UI like fetching a related entity name (the ScrapeConfirmation pattern). For "title + description + confirm/cancel + outcome" use ConfirmationCard inline.
- Attachment plumbing (US-010): `<CopilotAttachmentProvider>` wraps the CopilotKit children and exposes `useCopilotAttachment()` ⇒ `{ file, setFile, clear }`. A module-scope `currentAttachmentRef` is also kept in sync with `setFile/clear`, exposed via `getCopilotAttachment()` so non-React callers (e.g., a CopilotKit action handler running in client component scope but outside React tree at invocation time) can read the current attachment without re-subscribing. `<CopilotPopup>` accepts `children`, which render in a sibling `copilotKitModalChildrenWrapper` div INSIDE `ChatContextProvider` — so children can call `useChatContext()` from `@copilotkit/react-ui` to read the popup's `open` state. AttachmentBar uses that to hide itself when the popup is closed (it floats fixed at `bottom-[7.5rem] right-4 z-40` while open). PDFs are read via FileReader → base64 (string after `,` of the data URL); 10MB cap; `toast.error` on validation failures (sonner). Non-PDFs blocked by both file extension AND `file.type === 'application/pdf'`.
- Reading the attachment from inside a HITL component (US-011): use `const [attachment] = React.useState(() => getCopilotAttachment())` — a snapshot at action-invocation time is exactly what we want, and `useState`'s lazy initializer keeps eslint's `react-hooks/refs` rule happy (refs cannot be read during render). DON'T `useRef(getCopilotAttachment())` — eslint will flag every `attachment.current` read in JSX as "Cannot access refs during render".
- Async work in `useEffect` (lint pattern): wrap IIFE bodies in `void (async () => { ... })()` to suppress `@typescript-eslint/no-floating-promises`. Always pair with a `let cancelled = false; return () => { cancelled = true; }` cleanup so state updates don't fire after unmount.
- The `movements` table (drizzle/schema.ts:353) keys by `userId`, NOT by client/orgId — there is NO `client_id` column. When persisting bank-statement movements you scope the WRITE by user, validate the supplied clientId belongs to the org (FK check against `client.organizationId`), and embed the bank name in `descripcion` for traceability since the schema has no place for it. Future schema work might add `clientId` / `orgId` to `movements`; for now, treat `movements` as user-scoped and document this in any new persistence path. Also, `movements.id` is `text` (no `defaultRandom`) — generate via `crypto.randomUUID()` on insert.
- `scanBankStatement` (src/actions/scannerAi.tsx) ONLY EXTRACTS — it does not persist. The existing `/scan_pdf` page mirrors that: it shows the editable preview via `RenderPdfInfo` but never writes. To "save movements" you must add a separate persistence server fn (see `persistBankStatementMovements` in src/actions/copilot.tsx for the canonical pattern: getSessionWithOrg → assertCanWrite → validate clientId → parse Argentine montos/fechas → bulk insert).
- `RenderPdfInfo` (src/components/render-pdf-info.tsx) is a stateful editor: ingresos/egresos live in component state and there's NO callback to read the edited list. If you embed it in a HITL flow, persistence captures the ORIGINAL scanned movements, not the user's edits. Future work could lift state out via a `value`/`onChange` prop pair; until then, document the limitation in the HITL component's UX.
- HITL with auto-running side effects (US-011): when an action has BOTH an upfront extraction step (e.g., `scanBankStatement`) AND a confirmation step (e.g., `persist`), keep ALL phases inside one component. Pattern: phases `no-attachment | resolving | resolve-error | extracting | preview | submitting | done | failed | cancelled`. Use `useEffect` keyed on `phase` to trigger each transition. Use a `respondedRef = useRef(false)` guard so `respond(...)` can never fire twice (CopilotKit will throw if you double-respond).

(b) `persistBankStatementMovements({clientId, banco?, ingresos[], egresos[]})` — calls `getSessionWithOrg()` + `assertCanWrite(role)`, validates clientId belongs to the org, parses Argentine `monto` ("1.372.006,92" → 1372006.92) and `fecha` ("31/07/25" or "31/07/2025"), then bulk-inserts into the `movements` table with `id = crypto.randomUUID()`, `userId = session.userId`, `tipo`, `fecha`, `descripcion = "[banco] infoExtra"`, `monto = abs(parsed).toFixed(2)`, `tipoGasto = "Sin especificar"`. Skipped rows with unparseable monto/fecha are reported via the result `{inserted, skipped, clientId, clientName, banco}`. Note: the `movements` table has NO `client_id` column (see schema.ts:353), so the link to the client is best-effort via descripcion only — documented as a known schema limitation.

- **Learnings for future iterations:**
  - The PRD's literal hint "if scanBankStatement only extracts, add a follow-up persistence call" was correct: `scanBankStatement` ONLY extracts. Even the existing `/scan_pdf` route doesn't persist — it just shows the preview. We added the FIRST real persistence path for movements via `persistBankStatementMovements`. If/when the team adds a "save" button to `/scan_pdf`, it should call the SAME server fn for consistency.
  - The `movements` schema (drizzle/schema.ts:353) is keyed by `userId`, has no `client_id`, no `orgId`. The new server fn validates the clientId belongs to the org but only stores it in `descripcion` as `[banco] infoExtra`. Future schema work probably needs to add `client_id` (and possibly `orgId`) to `movements` — flag this when the next "movements per client" UI lands.
  - The `RenderPdfInfo` component is a self-contained editor: edits live in its internal state and there's no callback to read them. So `persistBankStatementMovements` saves the ORIGINAL scanned data, not the user's edits. Documented in the card subtitle so the user knows. Future work: lift state out of `RenderPdfInfo` via `value`/`onChange` props.
  - When a HITL component has an upfront async step (extract via Gemini, ~5s), use a `phase` state machine and `useEffect` per transition. Wrap async IIFEs in `void (...)` to silence `@typescript-eslint/no-floating-promises`. Use a `respondedRef = useRef(false)` guard since CopilotKit will crash if you double-call `respond`.
  - For the attachment, use `useState(() => getCopilotAttachment())` (lazy snapshot) instead of `useRef(getCopilotAttachment())`. eslint's `react-hooks/refs` rule flags every `.current` read in JSX as "Cannot access refs during render"; useState avoids that and gives us the same one-time-snapshot semantics we want.
  - The `resolveClientForCopilot` server fn is its own piece of glue: the existing IVA action duplicates this resolution inline, but for the scan flow the resolution must happen before the heavy extract step. Extract this into a sidecar fn so future actions that need name→id can reuse it.
  - The Argentine number-format parser: `parseArgMonto` accepts "1.234.567,89", "1234567,89", "1234567.89", with an optional "$" prefix. `parseArgFecha` accepts DD/MM/YY and DD/MM/YYYY (and DD-MM-YY[YY]). Both return null on garbage input so the caller can `skipped++` rather than throwing — keeps the bulk insert atomic.
